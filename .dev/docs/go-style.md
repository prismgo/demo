# Go 代码风格

本规范适用于工作区内人工编写的 Go 代码。优先保证清晰、简单、简洁、可维护和局部一致；规则未覆盖时遵循相邻文件与包的既有风格。

## 格式与导入

- Go 代码必须通过 `gofmt`，并使用 `goimports` 整理导入。
- 导入按标准库、第三方与项目包分组；仅用于副作用的导入单独分组并说明必要性。
- 禁止点导入；空白导入只用于明确需要副作用的入口或测试。
- import 默认使用包名；仅在名称冲突、包名与路径末段不一致或原包名含义不清时设置别名。
- import 别名应简短、稳定且语义清晰，同一包在项目内尽量保持一致；发生冲突时优先重命名更局部或项目特有的包。
- 不设置固定行宽。代码过长时按语义调整名称、参数或结构，不为凑行宽进行生硬换行。

## 命名

- 标识符使用 `MixedCaps` 或 `mixedCaps`，不使用下划线；`ID`、`HTTP`、`URL` 等常用缩写保持大小写一致。
- 名称长度与作用域匹配：局部变量、函数值、循环索引和方法接收者使用简短名称；使用位置离声明越远，名称越应明确。
- 包名使用简短、准确的小写单词，不使用下划线或复数；避免 `util`、`common`、`misc`、`api`、`types`、`interfaces` 等含义宽泛的名称。
- 避免名称重复已有上下文，例如包 `queue` 中使用 `Job`，不使用 `QueueJob`。
- getter 直接使用字段名对应的导出名称，不添加 `Get` 前缀；setter 使用 `SetXxx`。
- 单方法接口通常按行为命名为 `Reader`、`Writer`、`Formatter` 等；沿用标准库已有方法的名称、签名和语义。
- 方法接收者使用类型的一至两个字母缩写，不使用 `this`、`self` 或 `me`，并在同一类型的所有方法中保持一致。
- 避免遮蔽 `error`、`string`、`len`、`cap`、`make`、`new` 等预声明标识符。

## API 与类型

- 接口由使用方按实际需求定义并保持最小，不为预想扩展或方便 mock 提前创建接口。
- 实现方优先返回具体类型；导出的实现必须满足特定接口契约时，使用编译期断言。
- 接口按值传递，通常不使用接口指针。
- 参数仅在需要修改、共享身份或结构较大时使用指针，不为节省少量复制传递字符串或接口指针。
- 避免在导出结构体中嵌入实现类型，以免无意扩大公共 API。
- 优先使用有用的零值；`sync.Mutex` 和 `sync.RWMutex` 使用非指针字段且不公开嵌入。

## 控制流与错误

- 优先提前返回并先处理错误，保持正常流程低缩进；不使用无必要的 `else`。
- 非简单函数避免裸返回；命名返回值应服务于文档、延迟函数或可读性，而不是省略一行代码。
- 使用 `defer` 释放文件、锁和其他资源，释放位置应紧邻成功获取资源之后。
- 可失败函数以 `error` 作为最后一个返回值；成功返回 `nil` error。
- 错误信息使用小写开头且不加句末标点，专有名词除外。
- 增加调用上下文时使用 `%w` 包装错误；使用 `errors.Is` 或 `errors.As` 判断错误，不依赖错误文本。
- 同一错误只处理一次：记录、转换、降级或返回择一，通常不同时记录后继续返回。
- 哨兵错误命名为 `ErrXxx`，自定义错误类型命名为 `XxxError`。
- 不用 `panic` 处理常规错误；`MustXxx` 仅用于启动阶段无法继续的配置或构造过程。

## 上下文、数据与并发

- `context.Context` 作为第一个参数显式传递，不存入结构体、不自定义替代类型，也不传递可由普通参数表达的业务数据。
- 对需要保留或暴露的 slice、map 明确所有权；为避免外部修改内部状态或数据竞争，在 API 边界按需复制。
- 声明空 slice 时默认使用 nil slice；JSON 等协议明确区分 `null` 与 `[]` 时按契约初始化非 nil 空 slice。
- 避免可变全局状态；优先通过构造函数、参数或受控容器注入依赖。
- 避免 `init()`；确需自动注册等副作用时保持最小、确定且可测试，不在 `init()` 中启动 goroutine。
- 每个 goroutine 都必须有明确的退出条件或取消机制，并提供等待其结束的方式；禁止无人管理的后台 goroutine。

## 注释与文档

- 每个导出的包、类型、函数、方法、常量和变量都应有文档注释；注释以被描述的名称开头并写成完整句子。
- 非平凡的未导出声明在意图或约束不明显时也应注释。
- 注释重点解释原因、约束和易错点，不复述代码；代码变化时同步维护注释。
- 新增包或公共能力时提供可运行的 `Example` 或展示完整调用过程的测试。

## 测试与变更

- 相似输入场景优先使用表驱动测试，并在需要隔离或并行执行时使用命名子测试。
- 测试用例结构体优先使用字段名初始化，尤其是字段同类型、用例较长或需要省略零值字段时。
- 测试失败信息必须包含实际值、期望值和定位问题所需的上下文。
- 不设置固定函数行数；函数过长或过碎时通过职责与语义边界调整，而不是机械计数。
- 修改时遵循相邻代码的既有风格，不夹带无关重命名、格式化或重构。
